# K모델(KcELECTRA) 검증 기준 — 용도 기반 재정의

> 작성 배경: "모델을 테스트하기 전에, 흐름도에서 K모델이 **어떤 용도**로 쓰이는지
> 먼저 정하고, 그 용도에 맞는 검증 기준을 세운 뒤 테스트한다"는 원칙에 따라 정리.

---

## 1. K모델의 용도 (흐름도에서 도출)

전체 흐름도에서 K모델(KcELECTRA)의 출력이 쓰이는 지점은 **두 곳**이다.

### 용도 ① 질문 트리거 (주 용도)
```
KcELECTRA — 8요소 누락 분류
      ↓
필수 정보가 부족함
      ↓
필요한 내용만 사용자에게 되물음 → 답변을 원문에 반영 → 재분석
```
K모델은 단순 분류기가 아니라, **"사용자에게 되물을지 / 무엇을 물을지"를 결정하는
스위치**다. 어떤 요소를 "누락"으로 판정하면 그 요소에 대한 질문이 생성된다.

### 용도 ② 생성 입력 신호 (부 용도)
```
HyperCLOVA X — 최종 프롬프트 생성
   입력: 원문 + 사용자 답변 + [8요소 분석 결과] + 사용자 습관 + RAG
```
K모델의 분석 결과가 최종 생성 모델의 입력으로도 들어간다.

**→ 1차 모델 비교는 용도 ①(질문 트리거)을 기준으로 한다.** 파이프라인의 핵심 가치가
"부족한 정보를 되물어 채우는" 데 있기 때문이다.

---

## 2. 용도 범위 결정 — 누락(missing)만, 모호(vague)는 2단계

DB 스키마(`prompt_analyses`)에는 `missing`과 `vague` 컬럼이 따로 있다.
1차 검증은 **누락(missing)만** 다루고, 모호(vague)는 2단계 과제로 분리한다.

| 구분 | 누락 (missing) | 모호 (vague) |
|------|---------------|--------------|
| 정의 | 요소가 **아예 없음** | 요소는 있으나 **불명확** |
| 예시 | "번역 좀" → 대상·분량 없음 | "적당히 짧게" → 분량이 몇 자인지 불명확 |
| 판정 | 있냐/없냐 — 비교적 객관적 | 모호한지 여부가 주관적 |
| 라벨 일치도 | 높게 나옴 | 낮게 나옴 (라벨러 간 해석 차이) |
| 대응 | 없는 걸 물어봄 | 있는 걸 구체화하도록 물어봄 |

**1차를 missing으로 한정하는 근거:**
1. 파이프라인 핵심 가치가 "빠진 정보 채우기"(missing)에 있음. vague는 정교화 단계.
2. Ko vs Kc 우열은 missing만으로 충분히 가려짐. vague를 넣으면 "모델 차이인지
   vague 라벨 노이즈인지" 구분이 어려워져 비교가 흐려짐.
3. vague는 3-way 분류(명확/모호/누락)가 되어 데이터·모델·평가가 모두 복잡해지고,
   "모호" 케이스를 충분히 담은 데이터가 별도로 필요함.
4. 명확한 것(missing)부터 확립하는 것이 baseline으로 성능 바닥을 정하는 팀 원칙과 일관됨.

## 3. 검증 기준 — 왜 F1이 아니라 Recall 중심인가

용도가 **질문 트리거**이므로, 두 오류의 비용이 **비대칭**이다.

| 오류 유형 | 무슨 일이 벌어지나 | 심각도 |
|-----------|-------------------|--------|
| **놓침 (False Negative)**<br>빠진 요소를 "있다"고 오판 | 되묻지 않음 → **불완전한 정보로 최종 프롬프트 생성** → 결과물 품질 저하 | **치명적** |
| **헛물음 (False Positive)**<br>있는 요소를 "빠졌다"고 오판 | 불필요한 질문 하나 추가 → 사용자가 "이미 말했는데" 정도의 가벼운 번거로움 | 가벼움 |

**놓치는 것(FN)이 헛물어보는 것(FP)보다 훨씬 나쁘다.** 따라서 정밀도와 재현율을
동등하게 보는 F1은 이 용도에 맞지 않는다. **재현율(Recall)을 우선**해야 한다.

### 지표 체계

| 구분 | 지표 | 의미 | 목표 |
|------|------|------|------|
| **주 지표** | 요소별 **Recall** | 실제 누락을 얼마나 안 놓쳤나 | 최대화 (놓침 최소화) |
| **주 지표** | Macro **F2** | 재현율에 2배 가중한 F 계열 지표 | 최대화 |
| **감시 지표** | 요소별 **Precision** | 헛물음이 과하지 않은가 | 하한선 관리 (질문 폭탄 방지) |
| **비교 기준** | rule-based **baseline** | 신경망이 넘어야 할 성능 바닥 | Recall/F2 기준으로 baseline 초과 필수 |
| **참고** | Macro F1 | 기존 균형 지표 (보조) | 참고용 |

- **왜 F2인가**: F-beta에서 beta=2는 재현율을 정밀도보다 2배 중시한다. 놓침이
  치명적인 이 용도에 맞는 균형점이다. (F1은 beta=1로 둘을 동등하게 봄.)
- **왜 Precision을 버리지 않고 '감시'로 두나**: 재현율만 좇으면 모델이 "전부 누락"이라
  찍어 질문을 남발할 수 있다. Precision 하한선을 둬서 질문 폭탄을 막는다.

## 4. 데이터 구성 (1차 테스트 기준)

| 항목 | 내용 | 근거 |
|------|------|------|
| 총량 | 30건 (시드) | 파이프라인 검증용. 실사용 데이터 0건 상태의 리허설 규모 |
| 구어체 | 16건 (53%) | 실제 프롬프트는 구어체가 많음 → Kc의 구어체 강점 검증 |
| 오타 | 3건 (10%) | 실사용 반영 (요약해조/부착해요/해줄레) |
| 짧은 입력 | 5건 (17%, ≤10자) | 요소 대량 누락 케이스 → 질문 트리거가 작동하는지 |
| 길이 | 4~39자 (평균 22자) | 요소가 포함/누락 양쪽으로 고루 분포하도록 |

> **한계 명시**: 30건은 모델 비교 결론을 내기엔 부족하며, 파이프라인 동작 확인용이다.
> 실제 모델 선택은 실사용 데이터가 수백~수천 건 쌓인 뒤 수행한다.

## 5. 검증 순서 (왜 이 순서인가)

각 단계는 **다음 단계가 딛고 설 땅을 검증**한다.

```
1. 용도 정의        → 무엇을 위한 모델인지 먼저 확정 (질문 트리거)
2. 검증 기준 수립   → 용도에 맞는 지표 선택 (Recall/F2 중심)
3. 데이터 구성      → 용도·기준을 검증할 수 있는 데이터 (구어체·누락 케이스)
4. 라벨링 + 2인 검수 → 라벨 자체의 신뢰도 확보
5. kappa 측정       → 라벨 신뢰도를 정량 확인 (모델 학습 전에)
6. baseline 설정    → 넘어야 할 성능 바닥 확정
7. Ko vs Kc 학습·비교 → Recall/F2 기준으로 baseline 초과 및 우열 판정
```

**핵심**: 용도(1)와 기준(2)을 **모델 테스트(7) 전에** 확정한다. 이게 없으면
"F1이 높으니 좋다"는 근거 없는 결론이 된다. 용도가 질문 트리거임을 먼저 정했기에,
"누락을 잘 잡는(Recall 높은) 모델이 이 파이프라인에 맞다"는 판단 기준이 생긴다.

---

## 6. 팀 공유용 한 줄 요약

> K모델은 흐름도상 **사용자에게 되물을지 결정하는 질문 트리거**다.
> 누락을 놓치면(FN) 불완전한 프롬프트가 생성되어 치명적이고, 헛물으면(FP) 질문이
> 하나 늘 뿐이므로, 검증 기준을 **재현율(Recall)·F2 중심**으로 세운다.
> 1차는 누락(missing)에 집중하고, 모호(vague)는 2단계로 확장한다.
